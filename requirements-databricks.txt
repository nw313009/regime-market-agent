# DATABRICKS CLUSTER INSTALLS — these are the only installs permitted on a cluster.
#
# NEVER pip-upgrade pandas, numpy or pyarrow on a Databricks cluster. The runtime pins those
# three against its own Spark build; replacing them breaks Spark in ways that surface far away
# from the change and are painful to diagnose. That is why this file exists as a separate,
# deliberately short list instead of reusing requirements.txt (which pins pandas and numpy
# exactly for the local venv).
#
# Everything else this project needs — pandas, numpy, pyarrow, requests, PyYAML — is already
# preinstalled on the runtime.
#
# One nuance worth knowing: databricks-sdk ships WITH the runtime, so it is listed here as a
# version floor rather than a missing package. The runtime's bundled version may predate
# w.postgres.generate_database_credential, which the Lakebase pattern depends on. Upgrading the
# SDK is safe; it is not one of the three packages tied to the Spark build.
#
# Usage, either one:
#   %pip install -r requirements-databricks.txt        (notebook, at the top)
#   declare the same list in the job environment       (so workflow tasks get them)
#
# After installing, sanity-check that pip did not touch the pinned three as a transitive
# side effect: databricks-sql-connector declares pandas and pyarrow bounds, and the runtime's
# versions normally satisfy them. If pip reports uninstalling pandas, numpy or pyarrow, stop
# and resolve it rather than accepting the new environment.

# Markov-switching MLE. 0.14.6 is a hard floor, not a preference: earlier versions fail to
# import under pandas 3.
statsmodels==0.14.6

# XNYS trading sessions. Required because news-to-session mapping must use a real market
# calendar, never weekday arithmetic.
exchange_calendars==4.13.2

# Delta access over a serverless SQL warehouse, for code paths shared with the app.
databricks-sql-connector==4.4.0

# Version floor, not a missing package (see the note above): needed for
# w.postgres.generate_database_credential.
databricks-sdk>=0.125.0

# NO psycopg HERE — REMOVED AT C-1, AND IT MUST NOT COME BACK.
# psycopg[binary] 3.3.4 SIGABRTs the serverless notebook kernel at IMPORT time: the libpq
# extension abort fires inside psycopg/pq/__init__.py import_from_libpq and the kernel dies with
# exit code 134, before any code of ours runs. It is not a query failure and there is no
# try/except that catches it.
#
# The boundary this forces: Lakebase access (src/database/lakebase.py) is APP-CONTAINER ONLY,
# where the same package works and the pooled-OAuth pattern is proven. Notebooks and workflow
# tasks never touch Postgres — they read and write Delta, which is the architecture anyway
# (Lakebase is authoritative only for application state). The schema was created through the SQL
# editor rather than by calling ensure_tables() from a notebook.
#
# tests/test_import_boundaries.py enforces it: no module under src/ingestion, src/pipelines or
# src/models may reach psycopg through any chain of first-party imports. Adding psycopg back to
# this file would put the abort one stray import away from killing a workflow task.
